Stone Depot Systems Atlas

ClickUp is no longer a task tool at Stone Depot. It is the operating database for sales, projects, accounting requests, HR files, inventory counts, shipments and compliance, with Make.com acting as the integration layer and QuickBooks, Sprout, UTAK POS and Google Sheets each holding their own copy of core records.

This page maps what exists today and how work actually moves through it, so the ERP proposal can be built on the real system rather than on the org chart. It ends with the target: one system for Accounting, HRIS and Projects on one database, and the technical design behind it.

Two structural patterns

Everything is cloned per branch

Six sales spaces with identical lists and fields, five team spaces, five “2026 Documentation” lists, five A-Frame deposit lists, five disposal lists, five incident-report lists, five insurance lists, five QuickBooks companies, five ManyChat connections, and five-way routers inside Make (Facebook leads, weekly sales tasks, monthly partner emails cloned five times). A change to any process is made five or six times, by hand, and drifts.

Two generations run side by side

The 2024 Accounting space (lists per vendor, “Request for Payments [Internal]” with an 11-status chain) was superseded in late 2025 by the Procurement space (one form, 19 funding lists for 20 purposes) and in 2026 by the Accounting Team space. Both generations still carry open work, and staff must know which one applies.

Status sets are the schema

Most lists reuse one generic chain (to do → in progress → for review → complete). Where a real business state machine exists (leads, projects, incidents, funding, asset custody, shipments) it is encoded only as that list’s statuses, so it cannot be queried across lists or branches without a dashboard per list.

Shared role logins

Tasks are assigned to accounts such as BM-CEB, BM-LAG, OM, Acct1, Acct2, HR Generalist, HR Specialist, Auditor, Admin DVO, PC1-CEB, Sales-LAG and Sentinel (the automation user). A person can act under a role login, so the activity trail shows the role, not the individual.

3. Core workflows as they run today

Each flow below is drawn from the actual status chains, the SOPs in the Junior Programmer turnover docs, and the Make blueprints. Rounded boxes are ClickUp statuses; the owner and turnaround are written on the box where the SOP states them.

3.1 Lead to cash

  • Lead fields: mobile, email, acquisition channel and location are required on the form, plus project type and client history in the branch spaces; scope of work, contract amount and materials (a 78-option label) are optional.
  • Project fields add application, substrate, lead installer, helpers, turnover and completion dates, and the project documents: job order, conforme, estimate and 3D drawing, QA/QC, PCWC, fabrication punchlist.
  • Partner Program runs beside this: a public form → task in Partners (for approval → ongoing partner → partnership ended; rejections go to not approved; for validation is unused). Make emails monthly purchase totals read from the consolidated QuickBooks company, with the legacy branch company as a fallback, and a renewal creates a new task. The trigger field was removed from the list, so the monthly cycle has probably stopped; the next end-of-term decision is due 7 Nov 2026.
  • Branch KPIs (quota achievement, response time, new clients, columnar compliance) were built in Make as one Sales Specialist scorecard with a Davao route only: quota reads the QuickBooks TransactionList, new clients and response time read the ClickUp leads, and columnar compliance reads a Google Sheet. All sit in “Future Implementation” and are switched off.

3.2 Request to payment (funding, petty cash, reimbursements)

  • The form carries about 92 custom fields so that one form can serve 20 purposes routed into 24 lists (vendor quotes V1–V3, room rates, guests, container number, utility type, payee, etc.). Petty cash requests need only a summary-sheet link and a date range.
  • Refund Requests (for approval → for funding → funding complete → for liquidation → for recording → complete) follow the same shape. Supplier Accreditation was built in August 2026 and is not in use: for checking (Finance checks the documents) → for approval (no approver is defined) → accredited / rejected, with for renewal and expired set by hand.
  • Budget Planning: Make ID-04 creates one task per branch and back-office department (13) on 1 Aug for the next year; it has not run yet (first run 1 Aug 2027), and the 2027 tasks that exist were made another way. Monthly allocation: on the 1st, a parent task whose 12 currency fields hold budget and actual spending for six cost centres, plus six per-cost-centre tasks at 15:29 (from ID-05, misnamed “Facebook Webhook”). Every figure is typed by hand.

3.3 Hire to retire

The team has already specified the HR system it wants. The ClickUp doc “Stone Depot HR System — Complete Build Specification” (in the HR Meeting Agenda doc) defines 19 lists in 7 phases: Employee Master as the identity spine with restricted access, Recruiting with distinct rejection reasons, Hiring Requisitions, Talent Pool, HR Documents, Performance Evaluations with Pass/Fail (“Extend” held back pending legal advice), Check-Ins, Incident Reports, Disciplinary Actions, Grievances, Employee Movements, Cash Aid, Official Business, Offboarding with parallel clearance, Training, Engagement, and seven dashboards. Its stated rule: ClickUp originates workflow events; Sprout is the system of record for anything with a payroll or statutory consequence; Sprout Employee ID is the join key; no field is written in both directions. That document is, in effect, the HRIS requirements for the ERP and should be lifted into it rather than rebuilt, except where it disagrees with the live rules: its sanction ladder (5- and 15-day suspensions, cleansing at the end of the next calendar year) differs from Annex A and the ledger code (3- and 7-day, same calendar year), and that choice is the owner’s.

3.4 Incident report to sanction

Volumes: about 364 incident tasks in the list. Numbers come from a count of the list’s tasks per type with the year hard-coded (ID-03), so the same number appears on more than one case. The Infraction Ledger (Make data store ID-11) holds 476 records for 94 people against 142 Annex A rules; the “Recalculate Infractions” scenario ID-12 has run 215 times. The live list has 11 statuses; ClickUp does not enforce the transitions, and the arrows marked inferred are not confirmed by any source.

Native ClickUp automations (from the SOPs)

  • Form submission → rename task, set type, move to the working list, post a summary comment, add requester as watcher.
  • Scheduled → create the daily (08:00) and weekly (Monday 08:00) report tasks in each branch role list, then call a Make webhook that sets the dates.
  • Task created, status or custom-field change → call a Make webhook (application created → Branch Router; Resolution set; Approval Status = Approved; status = FOR TURNOVER). No scenario was found behind the PRE-ONBOARDING webhook.
  • Date-based → tag late / no report, post reminder and overdue comments.
  • Checkbox → status (Signed → Closed).

Where GPT decides

  • Branch from an address and position (applicants, leads, partners).
  • The Annex A section on the NTE. The reporter picks the incident type and code computes the offense count and sanction; only the legacy generator ID-08, still on, lets GPT reclassify the type.
  • Phone number normalisation on Facebook leads.
  • Parsing inquiry emails into task fields.

These are useful but they are business rules living in prompts. An ERP would hold branch territories and the offense schedule as data.

Data stores as shadow databases

  • Employee Info (98 rows): position, name, Sprout ID, emails, phone, birthday, branch, ClickUp option ID, ClickUp user ID, infraction counts, supervisor, 201 task ID. Used by NTE, ATD, birthday, auto-assign, approver scenarios.
  • Infraction Ledger (476) and Policy Library (142 rules): the disciplinary history and the offense schedule.
  • Sprout Employees (80): a mirror of Sprout, sync switched off.

Fragility observed

  • List IDs and user IDs hard-coded in ~60 scenarios; a renamed list or departed employee breaks silent paths.
  • Errors not surfaced to the task: lead-creation errors are swallowed by Ignore handlers and the installer calculator has no error branch. The ledger scenarios are the exception: they tag check-section and comment on the task.
  • Credentials hard-coded in 26 scenarios, and 41 webhooks with no scenario attached.
  • Shared automation identity (“Sentinel”) means automation edits and human edits are indistinguishable from the actor’s side.
  • The build spec itself lists idempotency and error branches as missing on every Sprout write.

6. Observed friction

These are things visible in the data, not opinions about ClickUp.

  1. Per-branch cloning multiplies every change. Six sales spaces, five team spaces, five-way routers in Make, six QuickBooks books, five partner-email clones. The team’s own note in Acct 1 (“Cancel QB Subscription for Branches”) shows the consolidation has started on the accounting side only.
  2. Identity is not shared. Seven employee copies (Figure 7); the join between them is a 98-row Make data store that one person maintains, plus ClickUp option IDs that must be added on every hire and exit.
  3. Sales reach accounting a week late and by hand. POS → QuickBooks import, scanning, receiving payments and checking is a four-step weekly chain per branch, and discount proofs and document requests are kept in per-branch Documentation lists. The sources disagree on whether those lists also log POS corrections.
  4. Approvals are advisory. “Approval Status” is a dropdown and “Approver” is a user field; nothing prevents a requester from setting them. The HR build spec flags the same gap for Cash Aid, which has an Approval Status field but no approver field, no Denied status and no enforced ₱5,000 cap.
  5. Sensitive data sits in task fields. 201 Files tasks carry SSS, TIN, PhilHealth and Pag-IBIG numbers, bank details and medical attachments, visible to anyone with space access. The build spec calls this out under RA 10173.
  6. Payroll outcomes are typed twice. ATD, cash aid and loan deductions decided in ClickUp are entered into Sprout by HR and verified by the Auditor as a separate status, because there is no write path.
  7. Financial consolidation is a task list. Q1 and Q2 2026 profit and loss, balance sheet and cash flow exist as per-branch and consolidated tasks “for review” in Acct 1, produced from five QuickBooks companies.
  8. Role logins hide the actor. BM-CEB, OM, Acct1, Acct2, HR Generalist, Auditor and Admin accounts are assignees; the audit trail records the role, not the person.
  9. Business rules live in prompts and scenario switches. Branch territories and the Annex A section suggestions are inside GPT prompts. The partner thresholds (₱200,000 entry, ₱500,000 re-application, ₱1,000,000 renewal) and the 25% discount are hard-coded in Make filters and six email templates, and the sources disagree on them.
  10. Reporting is outside the system. Compliance scores, KPI grades and payroll are in Google Sheets; the QuickBooks-based sales KPIs were built and never switched on.
  11. Two generations of finance workflow coexist. 97 items remain open in the 2024-style Request for Payments list while new requests flow through Procurement.
  12. Automations fail quietly. Lead-creation errors are swallowed by Ignore handlers and the installer calculator has no error branch. Scenarios that write to fields since renamed or deleted (Quota Meal, the audit ATD, the audit assignee) keep running and do nothing useful.
  13. Some processes have quietly stopped. Partner monthly statements and renewals (trigger field removed; the next end-of-term decision is due 7 Nov 2026), installer evaluations (unreviewed since mid-July 2026) and the Sprout employee sync (off, so new hires are missing from the Infraction Ledger and the web incident form). The full list, with the fixes that cannot wait for the ERP, is the “Fix now” table in Workflows/README.md.

7. Target: one system for Accounting, HRIS and Projects

Updated to your direction. Sprout and QuickBooks are retired and their functions absorbed. Inventory lives inside Accounting. Leads and project management form the third pillar. The branch POS is built in-house as part of the system, on the same database, so every counter sale is a sales invoice the moment it is rung up (decided 14 Oct 2026).

What each pillar holds

Accounting

  • Customer: customer master, estimate, sales invoice (every POS transaction is one, from the in-house POS on the same database), credit memo, payment, refunds, A-frame deposits with a due-back date and a rental fee, invoice adjustments with proof, EWT (2307), statements, partner purchase totals and the partner discount as a price rule.
  • Purchase: accreditation workflow over the core supplier master (documents with expiry, renewal job, unaccredited suppliers flagged on orders and quotes); purchase request from the branch, a ticket the Operations Manager or the BDO approves in My work, which creates the purchase order; bill created from the order by the Finance Specialist; bill payment when funds are available; container shipments received at landed cost (freight, customs, stripping); expenses as their own document, paid from petty cash, bank or card, never from stock; budgets checked at approval.
  • Inventory: items by category (slabs, consumables, stone care), each carrying its accounts; slabs as tagged pieces with dimensions; slab cut (one tag in, N out, cost split by area); material issue to a project, installer or branch cost centre, which replaces the ₱0 invoice lines; transfers tag by tag; counts whose variances become adjustments with a reason, reviewed by the Annex; valuation at landed cost.
  • Company: one chart of accounts with branch as a dimension, general journal, deposits, bank reconciliation for the five banks, inter-account fund transfers, funding requests (approval by purpose × branch × amount, up to three vendor quotes, disbursement, liquidation with a due date), petty cash funds and vouchers, budgets by cost centre (branch or department) with the yearly planning cycle and monthly allocations, leases with a renewal reminder, fixed assets (A-frames and tools included) and disposal, period close.
  • Reports: P&L, balance sheet and cash flow consolidated and per branch; sales by branch, specialist and channel; purchase; inventory; budget vs actual; KPIs such as quota achievement against a sales quota per branch.

HRIS (today’s workflow, kept end to end)

  • Recruitment: application form → applicant de-duplicated on mobile and email → branch routing from the territory table (plus a position → Back Office rule) → the HR build spec’s stages from screening to job offer; requisitions with GM approval, trade test, talent pool re-screened after 180 days, consent recorded.
  • Onboarding: pre-onboarding forms, PET, orientation, training, 3rd and 5th month evaluations, regularization, with computed deadlines and escalations as written in your HR build spec: the employee record is created at PET, evaluations fall at hire + 7, 90 and 150 days, and the GM is alerted at hire + 150 and + 170 days because an employee not decided by six months becomes regular by law (Art. 296).
  • Employee master: the 201 file with restricted fields (government IDs, bank, salary, medical) visible only to HR, the Finance Specialist, the General Accountant, the GM and the BDO, and to auditors only during an HR and payroll audit.
  • Timekeeping: time-in and out (biometric or mobile; one IN and one OUT per day, first tap wins, raw taps kept), schedules, leave, approved official business read as excused absence, and attendance rules that open incidents (AWOL, five or more tardies in a cut-off, abandonment). Absorbed from Sprout.
  • Payroll: semi-monthly runs, earnings, loan and cash-aid deductions, one deduction schedule shared by ATDs from disciplinary cases, audit restitution and cash aid, SSS, PhilHealth, Pag-IBIG and BIR withholding, payslips, remittance reports, payroll journal to Company. Absorbed from Sprout.
  • Requests and relations: cash aid (named approver, ₱5,000 cap), government loans, COE, payroll concerns; incident filed → NTE served → explanation → investigation → decision → signing → closed, with an appeal loop and the ATD becoming a deduction schedule; audit findings with the employee’s response and an amount split per employee; movements, salary changes, offboarding with parallel clearance and final pay.
  • Official business: a trip record approved by the employee’s supervisor, expense lines with receipts, a funding request for the cash advance or reimbursement, and the approved trip read by timekeeping as an excused absence.
  • KPIs: KPI definitions per position, scoring periods, stored scores and manual ratings, fed by queries over sales, leads, submissions, installer evaluations and attendance.

Projects and leads

  • Intake: Facebook Lead Ads, Gmail and web forms create leads, de-duplicated against the customer master.
  • Pipeline: lead → quotation → project with the real stages (fabrication, installation, rectification, turnover, documents, feedback), installer assignment and evaluation.
  • Partner program: applications checked by Marketing (documents) and the General Accountant (purchases), a term with start and end dates, monthly purchase statements computed from Accounting, end-of-term renewal or expiry, and the partner discount as a price rule on invoices.
  • Marketing: marketing requests as a ticket type, events with registrations that create customers, leads and redeemable vouchers, and a queue of social posts published by a scheduled job.
  • Tickets: the part of ClickUp that is genuinely work tracking, kept as one typed ticket module: scheduled report submissions, requests with a form per type, and ad-hoc tasks (see §8, Tickets). The board lives here; the ticket tables sit in core because every module raises tickets (see §8, Where the tables live).

8. Proposed technical design

Three big systems do not need three databases. The shared master list, employees above all, is the reason to keep them in one. The design below is one application, one PostgreSQL database with a schema per domain, and roles enforced both in the application and in the database.

How the one database is organised

  • Four PostgreSQL schemas, one database: core (branch, employee, user, role, permission, customer, product, supplier, territory, approval, ticket, notification, document template, document numbering, integration credential, audit log), accounting, hris, projects. A payslip points at core.employee, not at a copy. Which table goes where is listed under Where the tables live.
  • Master data lives only in core. No module keeps its own employee, customer or product table. This single rule removes the seven employee copies and the five branch encodings.
  • Every scoped table carries branch_id, plus created_by, updated_by and timestamps. A trigger writes old and new values to the audit log, which is what today’s role logins make impossible.
  • Document numbers are ERP-owned sequences per branch and per type (proposed formats such as CEB-SI-2026-000736, HR-PR-2026-0014, SD-OPS-IR-2026-0128). Today’s numbers are kept as legacy references: the per-branch invoice series (QuickBooks DocNumber such as DVO-175) map onto branch and sequence, and duplicated incident and audit numbers stay as legacy_ref beside the ERP’s own.
  • Status chains are data. core.workflow_status defines each document type’s statuses, allowed transitions, the role that acts in each status (and is assigned the item) and the turnaround time, which is exactly what your SOP tables describe. Changing a process edits a row, not five lists.
  • Rules are tables with effective dates: branch territories (province → branch), the Annex A policy library and sanction ladder, statutory contribution brackets, the partner program settings (thresholds, look-back, discounts, term length), KPI definitions and sales quotas.

Where the tables live

The workflow READMEs name tables in eight schemas (core, accounting, hris, projects, plus payroll, audit, sales and marketing). The design keeps the four decided schemas and places every workflow table in one of them by three rules:

  • A table belongs to the module that owns the process. If two modules need the same table, it moves to core. No new schema is added for a single workflow.
  • Between module schemas, a foreign key points one way: from the module built later to the one built earlier (core → projects → accounting → hris, the build order below). The other direction is a source reference (source_type, source_id), not a foreign key. Example: hris.cash_aid.funding_request_id references accounting.funding_request, and the funding request records source = cash_aid. Migrations then never form a cycle.
  • Code crosses modules only through ports declared in core, inside the same transaction, as described under Architecture inside each package. A foreign key across schemas is a data link, not permission to import another module.

Roles and permissions

  • One person, one account. Each user account belongs to exactly one employee and is the Google account on that employee’s record (see Authentication); shared role logins are retired. Role assignments carry a branch scope, so “Branch Manager of CEB” is a role plus a branch, not a separate account.
  • Superadmin reaches every module. One role, held by the Junior Programmer as system owner (decided 16 Oct 2026) and by at most two named accounts in all, sees all branches and all modules and administers users, roles and definitions. It is logged like everyone else and is not a way around approvals.
  • Permissions are module actions such as accounting.invoice.create, hris.payroll.run, projects.project.read, bundled into roles. The application checks them on every request, and PostgreSQL row-level security repeats the branch check on every query, so a reporting tool or a bug cannot leak another branch’s rows.
  • Permissions nest, and a person can hold more than their role. Decided 16 Oct 2026. A role grants modules. Inside a module, nested permissions name the record types and the actions on them, and conditions narrow them further: own branch, a status, a case type, an active audit. A person can also hold a personal grant on top of the role that others with the same role lack; the superadmin grants it, it is logged and it can carry an end date. The decided examples: the Branch Manager has Accounting, but only the purchase orders for their branch and their branch’s reports; the Branch Manager sees an incident only at the LOE step (NTE served), because the Branch Manager serves it to the employee in person; HR alone holds the deductions permission, and as a workaround to help HR the Finance Specialist may decide the ATD step on incidents.
  • Everyone can see their own access. Built 16 Oct 2026. My access shows what the person’s role opens: the modules and screens, the branch scope, whether salaries and IDs are visible, the incident rule, any personal grant, what was decided for the role, and where the person’s ClickUp spaces, lists and forms now live. People check it against their job and report what is missing or more than they need.
  • Sensitive columns (salary, government IDs, bank details, medical files) sit in restricted tables or views readable only by HR, Finance Specialist, General Accountant, GM and BDO, which answers the 201 Files exposure your own spec raised. Auditors see them only while an HR and payroll audit is active (decided 16 Oct 2026).
  • Approvals are data, not a dropdown. An approval chain names the role that must approve for each document type, or for each purpose × branch × amount on funding requests; the approver cannot be the requester; the approval is recorded with who, when and what version they saw.

Rules that keep it clean

  • Ticket or record? If it changes money, stock, payroll or a customer, it is a domain record with its own table. If someone must do, hand in or ask for something, it is a ticket. A ticket can create a record on approval and a record can raise a ticket, and each links to the other.
  • A request stays a ticket until it is approved. Decided 15 Oct 2026. A purchase request is a ticket; approving it creates the purchase order, so there is no order until someone with the authority says yes. Approvers outside Accounting (the Operations Manager, the BDO, the GM) act in the ticket modal in My work and are never sent into Accounting; the same modal opens the records whose approval sits inside them, such as a funding request (WF-08 keeps the approval chain on the request) and a fund transfer the GM executes.
  • Types are data, not code. Adding a new weekly report or a new request form means inserting a ticket type with its fields and schedule, not building a list, a recurrence and a scenario per branch.
  • One queue per person. Submissions, requests and tasks all land in the same My work screen, grouped by due date, which is the ClickUp feel to preserve. Reviewers get a review queue the same way.
  • No per-branch copies. One type, N tickets. Branch is a column on the ticket, so the compliance report and the role matrix in §8 work without five lists.
  • The outcome is derived, never typed. Each submission stores its timestamp and the review result; the outcome (on_time, late, no_report, exempt for a Sunday or holiday, agency_missing for the Graveyard report) is computed from them. A returned ticket keeps its original submission time for scoring. Each type states its Sunday and holiday policy explicitly (today the Columnar report is created on Sundays but never scored).
  • Creation is idempotent. The scheduler creates at most one ticket per type, branch and period, so a rerun cannot produce the duplicate October logbook DVO has today.
  • Migration. The 20 role lists that hold reports, the Monitoring list, the request forms and the Operations task lists import as tickets with their type, branch, dates, status and attachments. Tags map to outcomes: done → on time, late only → late, any no report → no report, closed while still tagged for submission → unknown. The six Google Sheets import as historical compliance rows and become the first year of the score; Graveyard and Toolbox “Late” imports as submitted with unknown timeliness, and the CDO Toolbox column is unreliable.

Incident reports: a case with a lifecycle, owned by its type

Re-checked in ClickUp on 14 Oct 2026. An incident is not a ticket: it is a record with a lifecycle, a sanction and a payroll consequence. The ERP keeps the lifecycle the team already runs, gives each incident one owner decided by its type, and lets payroll read the outcome instead of re-typing it.

What ClickUp holds today. One Incident Reports list in the Incident Reports space, fed by the Incident Report Form and the Railway web form. The reporter picks operations or policy, and Make ID-07 assigns the report by type; the legacy generator ID-08, still on, can overwrite the type. The list carries eleven statuses (for nte → for loe → for investigation → for decision → for atd → for nda → for signing → for appeal → for deduction → for audit verification → closed) and the fields that matter: type (operations-related or policy-related), reason for reporting (documentation or escalation), employee(s) and position, branch, date, time and place, details, violation, number of infraction (1st to more than 5), recommendation, resolution (no sanction, ATD, NDA, reminder, acknowledgement), final sanction (from acknowledgement to termination), amount to be deducted, a signed checkbox and attachments. Numbering is a count: Make ID-03 counts the list’s tasks of that type with the year hard-coded, so this year reached SD-OPS-IR-2026-0129 and SD-HR-IR-2026-0195, and the list holds the same number on two or three different cases several times over (0104, 0171, 0173, 0174). Two cash-aid deductions sit in the same list because it is where deductions get tracked. The HR Generalist is the assignee on most open items, which is the backlog the Junior Programmer’s August proposal (“Revision of the Incident Report System”) sets out to fix: HR owns policy incidents end to end, the OM owns operations incidents end to end, investigation, decision and resolution collapse into one stage, and incidents filed for documentation stop being escalated. Operations incidents also leak into the OM’s own task list (“IR: DVO Dmax pick-up”, “Recommendation Letter for DVO IR”), so there is no single place to see them.

  • Two boards, one table. Decided 14 Oct 2026: the Operations Manager and HR each get their own board over the same incident table. HR’s board is HRIS → Discipline and holds policy incidents only. The OM’s board lives inside My work, as an “Operations incidents” view beside the list and the phase board, and holds operations incidents from every branch, including those filed through the public form. A Branch Manager sees the cases of their own branch and the steps assigned to them (serving the NTE, obtaining the signature), also in My work, also in the modal. The Cases group in My work lists whatever waits on the signed-in role, sorted by the step that is due, late first.
  • One owner, decided at filing. The filer picks the type; the owner may reclassify once, and the change is logged. The owner carries the case from NTE to close, exactly as the August proposal asks. The hand-off that remains is a notification, not a reassignment: HR is told when an operations case ends in a deduction, and the OM is told when a policy case names someone on their floor.
  • Steps are data, not statuses. The same workflow_status table holds each step’s name, acting role and days. ClickUp’s “for X” statuses become the current step; “for atd”, “for nda” and “for deduction” disappear because the decision records the resolution and the documents and the deduction follow from it. Changing an SLA or adding a step is a row, not a list rebuild.
  • One row per employee involved. incident_employee holds the employee, the Annex A section, the offense count, the proposed and final sanction, the explanation and the signature date, so one incident can name several people, each with their own count and sanction. It replaces the Employee/s label, the employee-number text fields and the Infraction Ledger.
  • The policy library and the ladder are data. policy_section holds the 142 Annex A rules with category (A, B, C, D, Grave), handbook version and effective date; the old handbook numbering stays as an inactive version so 2025 cases can be mapped. sanction_ladder maps category × offense step to the sanction. Which ladder applies is the owner’s decision: Annex A and the ledger code (3- and 7-day suspensions, same calendar year) or the HR build spec (5- and 15-day, cleansing at the end of the next calendar year). The build spec adds controls: a repeat-offender flag, 26 suspension days in 12 months treated as grave, and GM approval before termination.
  • Documentation versus escalation. A report filed for documentation is acknowledged by the employee and closed with resolution acknowledgement, with no NTE and no investigation, so it can no longer be escalated by habit. Escalation runs the chain. Either way the record exists, is on the employee’s history, and can be reopened as an escalation with a reason. Whether documentation-only cases count toward the offense ladder is an open owner decision; today an acknowledgement does count.
  • Sources and notifications. The source is recorded: form, web form, audit finding, attendance, manual or anonymous. An anonymous report has no reporter and is visible to HR and the GM only; grievances are a separate table. A new incident notifies the owner and the Branch Manager; an overdue explanation notifies HR; an injury or death notifies the GM and sets a DOLE-reportable flag.
  • NTE, NDA and ATD are generated. The NTE is rendered from a versioned template with the handbook section and the prior-offense count. One counting function computes the count: same section, same calendar year (rule 3.01 counts by consecutive payroll cut-offs), No Sanction excluded, undecided cases counted provisionally, Grave counted once. It runs inside the decision transaction and recounts the employee’s later cases for the same section, which retires the Infraction Ledger data store and the recalculate scenario. The NTE deadline (issue + 7 days) is stored and drives an overdue alert. The decision renders the acknowledgement, NDA or ATD; the signed copy is attached to the case and to the employee.
  • The deduction needs no second person. A signed ATD creates a deduction schedule: employee, case, total amount, number of pay periods, first pay period and amount per period, split explicitly per employee. It puts one deduction line on each cutoff, visible on the payslip with the case number, and moves scheduled → posted → verified. Audit-finding restitution (WF-05) and cash aid (WF-07) use the same schedule. Payroll reads the case, so the “for deduction” and “for audit verification” statuses go, and the Auditor’s check becomes a report: deductions this cutoff against their cases.
  • Raised by the system where the facts already are. A slab marked broken at the saw (§8, Figure 15), a count variance above a threshold, a third missed driver delivery logbook in a quarter and a refund on a sales invoice each raise an operations incident with the record linked, so the OM investigates with the evidence attached instead of a retyped description. Attendance rules raise policy incidents the same way: AWOL, five or more tardies in a cut-off, and abandonment.
  • Migration. The IR list (about 364 tasks) imports with its type, employees, branch, dates, step, resolution and attachments; duplicate numbers are kept as the legacy reference and the ERP assigns its own. The ledger rows map to the employees involved by Sprout employee number. The cash-aid twins (HR-CA-…) and the SD-ATD-2025 items become deduction schedules, where the deduction belongs. The 2025 VI and IWPV series import as legacy cases that do not count toward the ladder.

When a role has more than one person

  • The least-loaded person gets it. The candidates are the active employees who hold the acting role with a scope that covers the item’s branch. The item goes to the candidate with the fewest open items assigned to them; on a tie, to the one assigned least recently.   • Reassignment stays possible. The assignee, a manager of that role and the superadmin can reassign the item to another eligible person. The move is logged with a reason and both people are notified. The next status change assigns again by the rule.
  • Never unassigned. If nobody holds the role for the item’s branch, the item goes to the fallback role named in the role configuration and the superadmin is alerted. When an employee is deactivated at offboarding, their open items are reassigned by the same rule.

The Operations Manager’s day with an operations incident

  1. Filed. A branch files an incident from the form, or the system raises one from a broken slab or a third missed logbook. The type is operations, so the owner is the Operations Manager. It appears at once in her My work under Cases and in the filed column of the Incidents board, with the NTE already drafted from the template and the employee’s prior cases counted.
  2. NTE served. She reads the draft, edits it if she must, and moves the card to NTE served. That move hands the Branch Manager a step: serve the NTE and upload the signed copy within five days. The Branch Manager sees it in their own My work; the OM sees the card with the days ticking.
  3. Explanation. When the signed NTE and the employee’s explanation are uploaded, the card moves to explanation by itself. If seven days pass without one, the card turns late and the OM is notified, and she may move on with that noted.
  4. Investigation. She moves the card to investigation, writes her findings against the record, and attaches evidence. Thirty days are allowed; the card shows how many are left.
  5. Decision. She moves to decision and must record the resolution (no sanction, reminder, acknowledgement, NDA or ATD), the final sanction and, for an ATD, the amount. The card will not leave the column without them. The acknowledgement, NDA or ATD is rendered from the template at that moment.
  6. Signing. The Branch Manager obtains the employee’s signature and uploads it. The employee may appeal within five days; an appeal moves the card back to decision with the Business Development Officer added as a second decider.
  7. Closed. She closes the case. If the resolution was an ATD, the deduction line is already waiting on the employee’s next payroll cutoff, with the case number on the payslip, and HR has been notified. The case counts in the employee’s history and in the branch’s incident report. Nothing is re-typed anywhere.

A policy incident runs the same seven steps with the HR Generalist in the chair and the OM informed. The only difference between the two is the owner, which is exactly what the August proposal asked for.

Accounting documents and the purchase flow

Decided 13 and 14 Oct 2026. The Accounting pillar is five groups of documents. Slab Cut and Material Issue are new and remove the ₱0 invoice lines; Expense is its own document; the POS is part of the system; and a purchase runs from a branch request to a bill payment through named hands. The Accounting Map draws the mechanisms and the React prototype runs them.

Customer

  • Estimate from the product master; accepted, it becomes the project and later the invoice.
  • Sales Invoice, one table for every sale. A counter sale rung up on the in-house POS is an invoice here the moment the cashier closes it, with the terminal and the tender on it; a project sale is drafted from the estimate. Posting writes the journal entry and the stock move together.
  • Credit Memo against a posted invoice: reverses revenue and VAT and reduces the balance; the invoice is never edited.
  • Payment: cash and card taken at the POS, transfers received at the office. It settles receivables and never touches income.

Purchase

  • Purchase request filed by the branch, a ticket. It goes to the Operations Manager or the BDO in My work; approving it creates the Purchase Order, and rejecting or returning it leaves no order behind.
  • Bill: on approval the Finance Specialist is notified and creates the bill from the order with one click, lines, supplier and payable included. A bill with no order, such as a forwarder or a utility, is recorded directly; receiving a container raises its landed-cost bill.
  • Bill Payment by the Finance Specialist when funds are available, full or partial, from a named bank; the requester is notified.
  • Expense: money out for what is never held in stock: delivery, installer pay, mobilization, meals, fuel, utilities, repairs, rent, fees. The category carries the account; an expense for a project lands in that project’s cost of sales; it is paid from petty cash, the drawer, a bank, the company card or a reimbursement. A liquidated funding request becomes one.

Inventory

  • Inventory report, first in the group: the branch sheet as a query. One row per tag for stones (date, supplier, PO, location, frame, side, tag, name, width, length, m², sold, on hand, defects, status, sold to or job order, date sold, remarks, cut date, and the IR, ATD and adjustment links), one row per item for consumables (received, issued, sold, adjusted, on hand), and a by-material summary whose Untagged column is the reconciliation the sheet’s Database tab did by hand.
  • Received from a shipment, a transfer or an approved adjustment, at landed cost; every slab is tagged at receiving.
  • Cut request, a ticket type raised from the project by the Admin Assistant or Sales with the slab tag, the pieces, the job order and a needed-by date. It reserves the slab and lands in the Admin Supervisor’s My work queue. Today this is a remark typed into the sheet that the supervisor scans for.
  • Slab Cut, prepared from the request with the pieces prefilled: one tag in, N tags out. The pieces must fit, their areas plus waste must equal the slab, the landed cost splits by area, the new tags print at the saw, and the request closes. Remnants stay on hand and sellable. A piece ticked as broken becomes a defect tag, a write-off Adjustment for the Annex and an Incident Report for the Operations Manager, raised by the cut itself and linked to the tag, the cut and the cutter (Figure 15).
  • Material Issue to a project, an installer or a branch cost centre: the document that replaces the ₱0 lines on invoices. The item’s category decides the account; the target decides cost of sales, operating expense, or “issued, unassigned”. The Branch Manager approves, never the issuer; no attachment rule.
  • Transfer tag by tag between branches; Count, which never changes stock but turns every variance into an Adjustment with a reason, posted by the Annex.

Company and reports

  • Funding requests, budgets, the general journal, bank reconciliation with statement lines matched or posted, period close.
  • Income statement, balance sheet, cash flow, changes in equity, AR and AP aging, purchases report, expenses report, project profitability. Every report is a query over the same journal, invoices, bills and stock; nothing in a report is typed in.

From a cut request to a deduction

The chain that today runs through a remark in the sheet, a supervisor scanning for remarks, an incident report filed by hand and an Operations Manager closing it after the authority to deduct. In the system it is one request ticket, one cut document, and two records the cut raises by itself; every link is a key in the database.

What the in-house POS changes. UTAK and Maya POS are retired. The POS is a screen of the same web app on a counter terminal, writing to the same database, so there is no import and no weekly matching. Because it issues the receipts, BIR accreditation of the POS and of the computerised accounting system is settled before the sales phase goes live rather than deferred. Role-based access for the purchase and inventory documents is deliberately not final: the team uses the prototype first and the roles are defined from that use. The prototype is published at el-varquez.github.io/erp-prototype-site for that: each person signs in as their role and checks My access.

Rules

  • One schema per package. Core owns core; each module package owns its schema and its migrations. Migrations run from the API repo in order, core first.
  • Import rule. Backend modules import core only. UI packages import their own API client and the ui kit. The rule is a lint check in CI, so a violation fails the build rather than waiting for a code review.
  • Cross-module effects stay in one transaction. A payroll run posting to the journal, an approved request creating a cash aid record, a ticket closing and scoring: all are service calls inside the one API process, with no queues or retries to build.
  • One login, roles decide the rest. The shell shows the modules a user’s roles allow. A Branch Manager sees projects, sales invoices and their team; an Admin Assistant sees submissions, the POS terminal and material issues; HR sees HRIS. The My work queue in the shell spans every module.
  • Superadmin is a role, not a bypass. It reaches every module and administers users, roles, ticket types, workflow and approval definitions, and reads the audit log. Its actions are logged like everyone else’s, and it cannot be the only approver on its own requests. Keep it on two named accounts at most.
  • Database access. The API connects with one database user; branch scoping is row-level security driven by the session’s roles; the superadmin session sets the all-branches flag, which is itself logged.
  • Environments. Development, staging and production for both repos; nightly backups with point-in-time recovery and a read replica for reports, as in Figure 9.
  • Later split, if ever. Lifting a module into its own repository means moving its package and adding an app folder; its schema, migrations and OpenAPI contract already stand alone.

Rules the stack must follow

  • Money is never a JavaScript number. Amounts are NUMERIC(14,2) in PostgreSQL and a decimal type (decimal.js or big.js) in TypeScript, from the request body to the journal line. A database check keeps every journal entry balanced before it commits.

  • Statutory tables are rows with effective dates. SSS, PhilHealth, Pag-IBIG and BIR withholding brackets, holiday calendars and the offense schedule are data, so the yearly update is an insert, not a release.
  • Row-level security is set by core, once. A middleware in core opens the transaction and sets the session’s user, roles and branch scope; every module query runs inside it. No module writes that code itself.

Architecture inside each package

Decided 12 Oct 2026: Clean Architecture in both repositories, without CQRS. Below is where each kind of code lives, how modules talk to each other, and the principles every pull request is checked against: no duplicated code, composition over inheritance, and dependencies that point inward.

Backend: use cases, not a command bus

CQRS is a pattern, not an ASP.NET feature, and NestJS has a package for it. It is still the wrong size here: a command bus, handlers and a mediator add indirection without buying anything at this scale. The shape below is the original Clean Architecture one, with four layers per module package and the dependency rule enforced by lint.

  • Use cases are plain classes. One class per business operation: ApproveFundingRequest, PostPayrollRun, ReceiveShipment, CloseTicket. A controller validates the body with the shared zod schema, calls exactly one use case, and maps the result. NestJS dependency injection is the only wiring.
  • One use case is one transaction. The use case opens the Drizzle transaction and sets the row-level-security session variables. Everything inside it, repositories included and ports into other modules included, runs on that transaction, carried by AsyncLocalStorage. Core provides this once; no module writes its own.
  • Reads bypass the domain. Lists, lookups and reports are query services that run SQL through Drizzle and return DTOs straight to the controller. This is the useful half of CQRS without any of the machinery.
  • A domain layer only where rules exist. Journal balancing, payroll computation, approval-chain evaluation, stock moves, workflow transitions and document numbering are pure TypeScript with no NestJS or Drizzle imports, so they unit test in milliseconds. Master-data CRUD such as supplier, product and branch goes through a controller, a small service and Drizzle, with no entity, repository interface or use case. Otherwise the team writes four files for every table in the system.
  • Cross-module calls go through ports declared in core. Modules never import each other, so core declares the interface, such as LedgerPosting or EmployeeLookup, the owning module implements it, and the API app binds them at startup. HRIS posts a payroll run to the journal through core’s port, inside the same transaction. In-process events are reserved for side effects that may happen after commit: notifications, compliance rescoring.

Frontend: features and hooks, not a service per component

Clean Architecture maps onto React, but a service per component is Angular’s shape and it fights React. In React the service is the hook, and the cache behind TanStack Query is the shared service that would otherwise be built by hand. If every component owned its own service, two screens showing the same invoice would fetch it twice and could disagree. So the unit that owns a service is the feature.

  • One folder per feature. It holds the feature’s model, its data hooks and its components. Components never fetch; they call a hook.
  • Services are hooks and pure modules. A hook such as useInvoice wraps the generated api-client with TanStack Query and owns loading, caching and invalidation. Pure logic such as totals, status rules and formatting is a plain module, imported from the shared package the API already validates with.
  • Two shared packages. ui holds presentational components such as the table, form field, money input and status pill, and knows nothing about any feature. app-core holds the cross-cutting hooks: session, permissions, notifications, the My work queue.
  • Server state lives in the query cache, UI state in the component. A global store exists only for session and shell state, if at all.
  • Screens are composed, not inherited. A page is a composition of feature components, ui components and hooks. There are no base components, no higher-order wrappers that hide props, and no class components.
  • Shell layout, decided 14 Oct 2026. An icon rail for the modules, a second column with the module’s screens in collapsible categories, a page header with breadcrumb, and a record’s detail inline under its list. Chosen from three prototyped variants; the other two are archived in the prototype.

Principles every pull request is checked against

  • No duplicated code. If two features need the same thing, it moves to the shared package and is imported. If two modules need the same thing, it moves to core. Nothing is copied and nothing is imported sideways. The second call site is the signal to extract; the first is not.
  • Composition over inheritance. No base classes for entities, services, repositories, controllers or components. Behaviour is shared by composing small functions, hooks and injected ports. A generic CRUD helper is a function that returns a repository for a table, not a class to extend. React components compose through props, children and hooks.
  • Dependencies point inward. Domain imports nothing from the framework; application imports domain; infrastructure and interface import both. The ESLint rule that enforces the module boundary enforces this direction as well.
  • One responsibility, named by the business. A use case does one operation and is named by it. A hook serves one feature. A component renders one thing. A file whose name needs the word “and” is two files.
  • Explicit over clever. No decorator magic beyond what NestJS itself needs, no reflection-based mapping, no generic abstractions with one implementation. A reader follows a request from controller to SQL by reading files top to bottom.
  • Test where the rules are. Domain rules get unit tests. Use cases get tests with in-memory implementations of their ports, which is the practical reason the ports exist. Controllers and screens get a small number of end-to-end tests.

Authentication: Sign in with Google, JWT, rotating refresh token

Decided 12 Oct 2026. There is no email-and-password login. Staff sign in with the Google account on their employee record; the API issues its own short-lived JWT and a rotating refresh token. Google proves who the person is; the employee master decides whether they may enter.

  • Google authenticates, the employee master authorises. The company runs on plain Gmail accounts, not a Workspace domain, so Google’s hosted-domain check cannot be used. The only gate is core.employee: a Google account may sign in if, and only if, its verified email matches an active employee row. Onboarding adds the email; offboarding deactivates the row and deletes the refresh tokens, and the person is out.
  • Authorization code with PKCE, handled by the API. The web app sends the browser to the API’s login route; the API redirects to Google with a state and a code verifier, receives the code on its callback, exchanges it server-side and verifies the ID token. Google’s tokens never reach the browser and are not kept: the ERP needs identity only, not Gmail access.
  • Access token: a JWT the API signs. Short-lived (15 minutes), signed with an asymmetric key that carries a key id so it can be rotated, holding the user id, employee id and the roles with their branch scope. The web app keeps it in memory and sends it as a bearer header. The API verifies it on every request and sets the row-level-security variables from its claims; nothing is looked up for it.
  • Refresh token: opaque, stored, rotated. A random value whose hash is stored in core.refresh_token with user, device, issued and expiry (30 days). Delivered as an httpOnly, Secure, SameSite cookie scoped to the refresh route. Every refresh issues a new pair and retires the old token; presenting a retired token is treated as theft and revokes the whole family. The table is the session list: logout deletes one row, offboarding deletes all of a user’s rows, and an admin can see and end sessions.
  • What this trades. A role change or a deactivation takes effect at the next refresh, at most 15 minutes later, because the access token is not checked against the database. That is acceptable here; if a case ever needs it to be instant, the refresh table carries a revoked flag the API can consult for that one user.
  • Machines do not use OAuth. The Facebook Lead Ads and Messenger webhooks, the Gmail pull and the biometric feed authenticate with per-integration secrets held in core (every inbound webhook needs an API key or HMAC signature), each with its own audit identity, so a webhook is never a user. The POS terminal is different: the cashier signs in with their own Google account on a registered device, so every POS sale is logged to a person.
  • Prerequisite. Every active employee, installers and branch staff included, needs a Google account on their employee record before go-live. A free Gmail address is enough.
